# Settled decisions

Decisions that shape the whole product, newest last in each section. A decision about one piece of work is in that work's goal. [How Thermite is planned](README.md) says how a new decision is recorded.

## Research and judging

| Date | Decision |
| --- | --- |
| 2026-10-14 | Agents never judge. Measurement, completion and promotion live in code that the agents cannot write. |
| 2026-10-14 | The harness owns all research state. Every agent call starts fresh from context the harness builds. Parallel workers are isolated, and a central, stateless planner assigns their experiments. |
| 2026-10-14 | The judge measures on a device first, and agents use it the rest of the time. Dedicated devices for each are configuration. |
| 2026-10-15 | Replaced on 2026-10-22 by hands-off promotion, below. Was: a confirmed win promotes on its own when no audit holds it; a gain above the contract's absolute audit trigger (15% by default) waits for the owner after its audit. |
| 2026-10-15 | No default caps. Nothing ends or cuts research short by default: no turn, submission, failure or wall-time limit. A campaign runs until its goals are met. A cap exists only when someone configures it. |
| 2026-10-15 | Files that a kit lists in `run.copy` are copied fresh into every run, owned by the judge and read-only to the run. |
| 2026-10-16 | No default time limit for a single command. A lane's processes live for the whole trial. |
| 2026-10-16 | Kits order their verifiers and gate expensive ones on cheap prerequisites (`priority` and `requires`). |
| 2026-10-17 | Test cases fit any kind of project. A case is a name and what makes it different. The score is a run's time, a rate, or a number that the check reports. |
| 2026-10-17 | A "hidden test" is a case the judge uses only to confirm a change that already looks better, never while it screens. |
| 2026-10-18 | A rig is a set of GPUs. Judge GPUs and agent GPUs are pools, and the split is set where a campaign is deployed. |
| 2026-10-20 | Each run has one experiment queue: the experiments still to try, in order, and a log of those tried, with their results. The planner coordinates it: it gives lanes work that does not overlap. The planner, the advisors and the owner add and reorder experiments; workers propose ideas for the planner to queue. Rules for the plan are set on the run's Planner tab. |
| 2026-10-20 | Every agent writes a journal and research notes. Thermite keeps its own knowledge base: each campaign has a folder with everything its runs produce, and reads other campaigns' folders only when the owner grants it. An outside knowledge base (such as GBrain) is optional: a sync target and a source of outside context. |
| 2026-10-27 | The knowledge base lives on control, with all its storage and search indexes: one collection for each campaign, then runs, then slots, then items. Every agent reads it over MCP; the roles a campaign lets write each write into their own slot and never change another writer's items. An item is a blurb or a file (a reference an agent downloaded, or a doc an agent wrote). Writes arrive as durable events on NATS. A run continues its campaign's collection or starts fresh; other campaigns' collections are read only, by grant. ([175](goals/_completed/175-knowledge-base.goal)) |
| 2026-10-19 | Research workers search all of a run's research and write files. The harness builds a research folder from its records (read-only to workers), and each lane keeps a working area across its trials; the other lanes see a lane's files when its trial ends. A research run's output is its report plus the whole folder. Findings carry a summary and why they matter, and code checks them against verified claims. ([062](goals/_completed/062-research-folder.goal)) |
| 2026-10-22 | Hands-off by default; the owner is asked only where they set it. A win the judge confirms is promoted with no owner step, in every mode; an auditor, when one is set up, is the last step, and its block stops the win and says why. Built-in owner gates (a gain above the audit trigger, declared flaws) ask the owner only when the campaign is set to ask. The owner's words: "The system is supposed to be hands off for me. Theres no need for me to step in an confirm every win... cause thats why we have judges and auditors... I shouldn't ahve to do anything (Unless I set it to ask me) by default it should auto... research..." ([079](goals/_completed/079-thermite-overhead.goal)) |
| 2026-10-22 | The model provider decides when agents can work: its errors are sorted by kind. A rate limit waits for its time; no credits, a refused key or a failing model check stops the run's agents and asks the owner, with the provider's words; a passing fault backs off. A research run's clock stops while its agents cannot run. ([079](goals/_completed/079-thermite-overhead.goal)) |
| 2026-10-25 | Lanes may keep working while the judge works: a campaign's setting (`lanes.keep_working`), off by default, which a run turns on and off with a rule. On, a lane's next trial starts when its last one ends and a round ends when its trials end; `budget.max_open_attempts` bounds the changes waiting for the judge. Off, lanes wait for the judge's verdicts. The judge should work in parallel where it can, and a change written on an older champion is carried to the new one ([135](goals/_completed/135-lanes-and-judge-throughput.goal)). |
| 2026-10-25 | No lane sits idle behind another lane's trial: a round ends once every free lane has run its trials, and a lane still on a trial joins the next round. A run that waits for verdicts still waits for the judge ([goal 136](goals/136-no-idle-lanes.goal)). |
| 2026-11-07 | The teachers in Claude Code and the Codex CLI research outside the run with their program's own web search and fetch, beside the knowledge base and the run's code (the owner, issue 56: "claude code and codex provide their own web search and fetch tooling, those should be enabled for teachers... plain and simple"). No other advisor gets them. Thermite's own open fetch (`fetch_domains` `"*"`) still keeps the knowledge base away (goal [232](goals/232-teachers-research-the-web.goal)). |
| 2026-11-08 | Those teachers search the web every round and bring outside sources in (the owner: "claude and codex should search every round. EVERY ROUND. you always go to bring external resources in when possible"). Their instructions say so, and code sends a teacher whose turn ends with no search back to search (goal [232](goals/232-teachers-research-the-web.goal)). |

## Rigs and deployment

| Date | Decision |
| --- | --- |
| 2026-10-14 | Replaced in part on 2026-11-04 by a rig of one core and its runners, below. Was: a rig is a harness container and a supervisor container. Everything runs on Kubernetes or under docker-compose or podman-compose (this part stands). |
| 2026-10-14 | The harness reaches only DNS, the internet and its model endpoint. The supervisor reaches the internet, its harness, control and, optionally, a knowledge base. The supervisor does all git operations. |
| 2026-10-14 | One central control service, with a dashboard, an API and MCP. Supervisors report to it, and it can pause, reset and assign rigs. |
| 2026-11-02 | Replaces "Each project has its own results repository. The project's key is read-only." (2026-10-14). A campaign's creator chooses where its runs' work goes: branches of the project's own repository (the default), a separate results repository, or control alone. Each run pushes `thermite/<run>/champion`, a commit for each champion, and `thermite/<run>/lane-<n>`, each lane's attempts as patches; only branches under `thermite/`. The push uses a Git access with write rights that the supervisor alone holds. The run's record (events, notes, the knowledge base, the ledger) stays on control ([185](goals/185-a-runs-work-in-git.goal)). |
| 2026-10-16 | Thermite is self-contained. Campaigns, kits and rigs are managed through control. Infrastructure belongs to whoever runs it. |
| 2026-10-17 | Control sets rigs up itself. Given an SSH key or a kubeconfig, it checks the place, installs what is missing (only when the owner says yes), deploys the rig and manages it. Rigs still report by dialing out. |
| 2026-10-18 | Control refuses a pre-made Kubernetes slot whose network rules do not keep the harness off the cluster. "Join a rig yourself" is an optional third way to add a rig. |
| 2026-10-27 | A rig on a machine or a cluster reaches control's NATS server on NATS's own port, over TLS (a second port beside control's HTTPS), with a key the rig's supervisor made and registered over HTTPS; control keeps the server's users file. Secrets go to a rig sealed to its own key, only when they change. The dashboard's push is Server-Sent Events from control. ([168](goals/_completed/168-message-bus.goal)) |
| 2026-10-29 | Replaced in part on 2026-10-30 by "bus only", below: rigs no longer report over HTTP. Was: control needs its NATS server once its own copy of the rigs' events moves to JetStream (goal [168](goals/_completed/168-message-bus.goal)): rigs may still report over HTTP, and control publishes their events. Control's table of commands stays as its own signed record; JetStream snapshots back the streams up. |
| 2026-10-30 | Bus only. A rig and control talk only over NATS: its reports, commands, config, live view and knowledge base. A rig that can't reach the bus doesn't work and is shown as broken. HTTPS keeps only a rig's first registration of its keys and the large files (kits, exports, bundles) that stay on git and HTTP. A RunPod rig joins the bus through the leaf node in its pod. The owner's words: "NATS is the only supported way. Bus only. If bus doesn't work RIG doesn't work and is considered broken." ([168](goals/_completed/168-message-bus.goal)) |
| 2026-10-30 | Control keeps a list of addresses and ports that cluster rigs' harnesses may reach beside the internet, set by the owner. Control writes it into each rig's network rules, and it accepts a pre-made slot whose rules open exactly listed addresses and ports. ([172](goals/172-build-v011.goal)) |
| 2026-11-04 | A rig is one core and any number of runners. The core runs on any machine, a CPU-only one too: the supervisor, the ledger, the project's git, the planner, every lane's agent program and workspace, and the judge's decisions. A runner holds one target resource (a GPU of a machine, a pod on a cluster, a GPU pod on RunPod that exists only while it works) and just enough to take a run and give back its result, isolated as today. Lanes get `run_experiment`, which runs their change on a runner and never counts, and `submit_experiment`, which sends it to the judge; the judge's builds and measurements run on runners too. A runner serves a shared first-come queue or is dedicated to one agent, and runners come and go without pausing the run. This replaces the same day's leader and followers, whose code was backed out; a rig of one machine is a core with its own runner, as before ([206](goals/_completed/206-core-and-runners.goal)). |
| 2026-11-10 | A rig's harness and supervisor are updated together, so neither keeps code for an older partner on the same rig. A core and its runners, on other machines, keep theirs. A rig's log lines reach control, in a table of control's own store with SQLite's text search (goal [257](goals/257-find-the-fault.goal)). |
| 2026-11-12 | A run owns its agents and its share of compute, machines are a pool, and no screen of the dashboard shows a rig (goal [258](goals/258-runs-own-their-resources.goal)). The owner accepted it into v0.3.0 as the first work of the new app: the back end is rebuilt on that model, and the screens are then built once, from the mockup the owner agreed ([the app's build plan](app-build-plan.md)). Its design is written and agreed before any code. Until it ships, a rig is what a deployment runs, as the decisions above say. |
| 2026-11-12 | The agents work in the control plane ([goal 258's design](goal-258-design.md), agreed by the owner): their loops and the writing of code, with each worker in a zone of its own there, Claude Code among them. A machine runs one runner, which does only what needs the machine: builds for the device, measurements, a worker's experiments on a device. A change reaches a machine as a commit, and no sign-in for a model reaches a machine. The control plane has its own sandboxes. In v0.3.0 the runner is one program in one image, so the container stays the wall; a runner with no container engine is looked at for v0.4.0. This takes the place of "the harness reaches only DNS, the internet and its model endpoint" and "the supervisor handles all git operations" when goal 258's ninth step ships; until then those hold. |

## Providers and models

| Date | Decision |
| --- | --- |
| 2026-10-17 | A model provider is entered once: name, type, base URL and key. Its models are listed from the provider. Keys are sealed and sent only to the rigs that use them. |
| 2026-10-17 | Each rig picks its worker harness and its model as two separate choices. |
| 2026-10-18 | Each agent role (the planner, the workers and each advisor) can have its own model and effort. |
| 2026-10-18 | A Claude subscription runs only inside Claude Code, never in another program. Its token goes in Claude Code's environment. Claude Code is in an image only when the image is built with that option. |
| 2026-10-18 | ChatGPT works through Sign in with ChatGPT. Control keeps the refresh token sealed and is the only one that renews it. Rigs get one-hour access tokens. |
| 2026-10-18 | At a subscription's usage limit, agents wait for the reset. They never use paid credits. |
| 2026-10-18 | A subscription serves only its owner's own Thermite. A Thermite that several people use takes API keys. |
| 2026-10-20 | MCP servers are added once in Settings, with OAuth, a key, a client ID and secret, or no sign-in, sealed as keys are. A campaign's kit names the servers its agents use and which agents get each one. Control gives a rig only the servers its runs name; the harness makes the calls for workers and the planner, the supervisor for the advisors, and the secret stays in their memory. This replaces the outside knowledge base of 065: GBrain is an ordinary MCP server. ([068](goals/_completed/068-mcp-servers-for-agents.goal)) |
| 2026-11-10 | A model provider is added from a catalogue: a list of known providers as data, made from the registry of the maintainers' fxbot and shipped with each release. An entry is a preset of one of the provider types that rigs know, never a new type, with its address, its key page and the steps there. A key is checked with the provider when it is added, and a refused key saves nothing. Control fetches no list while it runs. A provider's logo ships only with its licence checked. This replaces how a provider is entered (2026-10-17); keys stay sealed and go only to the rigs that use them. The sign-ins of v0.3.0 are a Claude subscription's token and ChatGPT, as before, and OpenRouter; each later sign-in first answers whether the account is for the owner's own Thermite alone (goal [245](goals/245-providers-and-set-up.goal)). |


## Control and operation

| Date | Decision |
| --- | --- |
| 2026-10-16 | The dashboard is for a human operator. Every decision it asks for shows what is decided and what each choice does. |
| 2026-10-16 | Screens are chosen from mockups. Every form label has a description. |
| 2026-10-16 | Campaigns are operated only through control: the dashboard, REST, MCP or the CLI. |
| 2026-10-16 | The owner mints the admin token, and control keeps only its hash. An operator token lets agents assign, pause, resume, redirect, reset, export and message agents. Approvals, audits and reviews stay the owner's. |
| 2026-10-18 | Cards, call-outs and reports are written in Simplified Technical English. |
| 2026-11-01 | Everything is kept everywhere by default. Users design their own retention policies, with full control over what each removes, where and when. Exports are made only when a run ends or when someone asks for one, never on a timer, and are removed only by hand from the Exports menu. ([125](goals/_completed/125-code-to-the-conventions.goal)) |
| 2026-11-07 | A run in progress is repaired in place, never restarted. A fix reaches the running run when its rig moves onto the new images; an experiment that a fault of Thermite's cut short, or that it judged wrongly, goes back to the run's queue or is judged again, with why in the run's history; and the run goes on. Where control has no way to make such a repair, that is a gap to fix in Thermite ([221](goals/_completed/221-repair-a-run-in-place.goal)). |
| 2026-11-10 | The dashboard becomes a web app on the UI system of the maintainers' fxbot: React, shadcn/ui's components, Tailwind CSS and Geist. It is a client of control's API alone, so every action and every read of the dashboard is in REST and MCP, and control serves its built files. It replaces the pages drawn on the server, which stay in use until the new dashboard covers every screen, and take fixes only once its build starts. This replaces CONVENTIONS.md's rule of 2026-10-24, "no frontend framework". The owner's words: "I want to utilize the UI/UX system I started for fxbot ... including it's v0.8.0 provider login setup system. Its way cleaner and nicer than our ux." (goals [242](goals/_completed/242-v030-review.goal) and [243](goals/_completed/243-web-app-base.goal); the [UI refresh guide](ui-refresh-guide.md)) |
| 2026-11-10 | Screens follow one set of rules ([the rules for screens](ui-refresh-guide.md#4-the-rules-for-screens)): one job for each screen, one home for each fact, one sentence at most under a heading. A field's description is one hint under it; an icon to hover stays only where a column's or a figure's meaning is not plain, so "every form label has a description" (2026-10-16) stays true. Every screen works at 390 pixels wide. Light and dark follow the operating system. A new control opens on Set up Thermite. |
| 2026-11-10 | Control's store moves from SQLite to PostgreSQL (the owner: "postgres"), with the work of goal [258](goals/258-runs-own-their-resources.goal): a control plane of several services needs a store that several writers share. A run's records can then be asked in plain SQL, read only, over a small set of tables that are a contract; Thermite writes no query language of its own. This replaces the SQLite store for control of 2026-10-14. The message bus stays the transport and the log of events. |
