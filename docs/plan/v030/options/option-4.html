The conventions

Taken from fxbot as they are, so that both products read the same way. Its conventions open with four choices, and with one more line: a smaller solution that does the job beats a rule kept from an older design.

Simplicity over complexity

Three rules place every file. A boundary is a line in a package.json. An action is written once.

Small over huge

Seven packages. A file does one job and reads in one sitting. An eighth package needs a second real consumer.

Light over heavy

Few dependencies, each with a reason. A plugin that is not added costs nothing: no process, no table, no code in the page.

Performance over other things

What a person waits on stays fast: a screen's first view, an action's answer, a job's start. A change says what it adds to those.

One thing is above all four: agents propose, and code they cannot write measures and judges. No convention trades that away.

Core or plugin

The default is plugin

Before a feature is built, ask: core, or a plugin? Its goal says which, and why.

Core is only what every run needs, what plugins plug into, and what Thermite needs to run.

What a plugin may count on

  • The core never imports or names it. Which plugins a new install gets is a list, as data.
  • Thermite's own plugins use the same API as anyone's.
  • When it cannot do what it needs, the API gets the smallest hook for it, on the day a real plugin needs one.
  • A release that breaks the API says so in one list, and a plugin names the oldest Thermite it runs on.

What the core may count on

  • A plugin that is not added costs nothing.
  • A plugin's data is its own, in tables or files that it makes and removes. Never in a migration of the core.
  • Removing a plugin leaves the core working.
  • Never open to a plugin: measuring, verdicts, promotion, the record's writer, the wall, who may do what.

Where Thermite goes its own way

No SDK

fxbot is put inside other products. Nothing embeds Thermite: other things talk to it, through the door.

Two programs, and a bus

fxbot is one server. Thermite has a second program, on other machines, so it has one more boundary, and NATS for it.

Tests

fxbot checks each feature by hand. A wrong rank in a statistics routine is not found by hand, so what a verdict rests on has tests.

The three rules

The whole tree follows from these. No fourth rule is needed to say where a new file goes.

1. A package is a program, or what two programs share

Five programs: the control plane, the runner, the command line, the dashboard's app, the website. Two shared things: the core and the design system. Seven packages.

2. Each boundary has one folder in the core

What two programs say to each other is written once, in core. The control plane and the runner never import each other.

3. Core or plugin

What every run needs is in the packages. What an install may leave out is a plugin. The core never names a plugin.

One action, written once

Take "pause a run". Today an action's route, its MCP tool, its command and its page's form are written apart. Here it is one entry and one function.

1. The entry core/api

Its name, its input and answer as schemas, who may call it, its words. It also names its route, its tool and its command.

2. The function control/scheduler

The rule: what pausing does, when it is refused. It is in the folder of the thing it changes, never in the door.

3. Made from the entry

  • the REST route, in door/rest.ts
  • the MCP tool, in door/mcp.ts
  • the thermite command
  • the client's call, for the app
  • its reference page
  • Thermy's tool

MCP has a second, separate use: a run's own tools, which a worker calls (submit a change, run an experiment, write a note). Those are not the door. They are in control/agents, and a harness plugin hands them to its program.

What stays on a machine

Only what needs the device: the build for it, the judge's clock and its measurement, a worker's experiment. The wall between a change and the judge's files is the runner's.

What never leaves the control plane

The record, the agents' conversations and their keys, the judge's decision, promotion. A machine that is lost loses a job, not a run.

Who may say what

Every runner signs in with a key of its own. The control plane writes the server's users: a runner may publish and read only its own subjects. That table is a contract, in core/bus.

Nothing is lost when a side is away

A measurement in flight ends on its machine while the control plane restarts, and what it reports waits on the bus. The record goes on from its place: no event twice, none skipped.

Why not HTTP between the planes

A machine needs no API of its own, a message outlives a restart on either side, and one place says who may reach what.

How it gets there

The run sheet's 35 steps keep their order. One step is added first: set up the workspaces, and move what lives on unchanged. After that, each step builds into the new packages, and src/ shrinks until it is empty.

Workspaces. web, the site, the kits move. The contracts and the bus become core.

What I am least sure of

One core, or two

core holds what a browser may load and what only Node runs (the bus's client). Entries and a check keep them apart. Two packages would make the line physical, for an eighth package.

Thermy

By the rule it is a plugin. It needs a place in the page, a fourth kind of hook that nothing else needs yet. So: in control/agents first, a plugin when a second one wants a place in the page.

The control plane as one package

It will be the large one. Its services are entries, not packages, until one needs an image or a release of its own.
