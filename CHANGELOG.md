# Changelog

Each release of Thermite, newest first. Versions 0.x make no upgrade promise: read [Known limits](docs/_site/src/content/docs/reference/known-limits.md) before you upgrade.

## [Unreleased]: v0.1.1

### Operate

- The tests are in `tests/`, in folders that mirror `src/`, with their helpers, fakes and stand-ins in `tests/helpers/` (goal 160). `npm test` stops if it finds a test file in `src/`.
- An update that migrates a database can be undone: the harness copies the ledger, and control copies `control.db`, beside themselves before a migration changes them (`<file>.v<version>.<time>.copy`, the two newest kept). A newer database met by older code is refused with the copy to restore. Control's store now has a schema version; a store v0.1.0 wrote counts as version 0, and is copied before its first migration (goal 173).
- A number setting whose value is not a number, or is outside what the setting takes, now stops its service at start with the setting's name and what it takes, for example `THERMITE_POLL_SECONDS takes a number of seconds above 0, not "30s"`. Before, the value was used as it came: `THERMITE_EXPORT_MINUTES=6O` stopped the exports for good, and an empty value meant 0. A deployment that set such a value fails at start after the update; [Settings](docs/_site/src/content/docs/reference/settings.md) says what each setting takes. An empty number setting takes its default (goal 164).
- `thermite status` exits with 1 when the harness answers with an error. A rig's settings file the harness can't read is kept aside, logged and reported, where the defaults took its place in silence before. The supervisor logs a refusal of its calls to the harness about the advisors once, with its status (goal 164).
- Removing a rig control set up, on a machine or a cluster, is refused while any of its results waits on it, as a RunPod terminate and a full reset already were: the page says what waits and to export first. `discard <rig>` typed instead removes a rig whose results can't leave, and the audit log records what had not left (goal 165).
- A full reset no longer waits an hour and fails on a judge job queued for a run it paused: it waits only for jobs under way and jobs of runs that still run. On the one-container rig image, the supervisor starts again after a full reset: root makes its files again before each start (goal 165).
- "Update to control's version" keeps its step and the runs it paused in control's store (schema version 2: the store is copied before it migrates). A control restarted in the middle of an update ends it at start and resumes those runs, and the rig's history says why (goal 165).
- Control looks at RunPod rigs as soon as it starts, so a pod that passed its spend limit or idle stop while control was down is stopped at once, and its notes say so. Control checks those limits only while it runs; Known limits says so (goal 165).
- A Pi worker's reply longer than 8,000 characters reaches Live cut and marked `[cut]`, where it was lost; every program's long lines end the same way. One line of a kind control does not know, from a newer rig, is left out and counted instead of stopping the rig's live view for good (goal 171).
- The supervisor fetches a waiting command's content once, then only its id, where it fetched every pending command whole every 5 seconds. A command whose content is still being fetched, such as a long model download, is kept alive by control for up to 24 hours after it was issued, where it expired after its hour (goal 171).
- OpenCode and Claude Code take their prompt on stdin, as Codex does, so a long brief or planner context no longer stops the program from starting on Linux, which allows 128 KiB in one argument (goal 171).
- The agent programs' trials behave alike (goal 125, T7). A Codex trial whose ChatGPT plan is full now waits in its own conversation and goes on, as OpenCode's on a ChatGPT route does, where it ended at once. An OpenCode trial's brief states its turn cap, as Claude Code's and Codex's do, and a trial that reaches it says so in words; after a submission, the cap waits out the grace that records it. A harness image without OpenCode's binary ends an OpenCode trial, and its model check, with words that say so. A one-prompt call stopped before it starts runs nothing. Claude Code's limits note states its own memory, measured in the real Claude Code acceptance (about 350 MiB), where it repeated OpenCode's.
- Every git call has a time limit of 30 minutes, unless its caller sets a shorter one (a repository probe: a minute); a push to the results repository or a fetch of a project had none. A failed call names git's subcommand with git's own words (goal 125).
- Each image upgrades its base's system packages when it is built (`apt-get upgrade`), so an image built again takes the distribution's fixes, not only a release's build without the cache. The harness's build cache keys on the image's packages, so a lane's first build on an image whose packages changed starts without its cache (goal 125).
- A run's name is used once on control, on every rig and in every ledger: **Start a run** and New campaign number a campaign's runs across all rigs (a second rig's run is `sort-speed-2`, no longer `sort-speed-1`), and an assignment whose name was used, over REST, MCP or the command line, is refused with a name to use instead. Control keeps each champion's patch by ledger, so a run of a reused name from before a full reset never stands in for it. Control's store goes to schema version 3 (goal 170).
- A run's export holds the events about its attempts and the judge's jobs for it, each `verdict` among them, where it held only the events that named the run (goal 170).
- Every log line has a `level`: `debug`, `info`, `warn` or `error`, and the lines that say something failed are `error`, the ones about a refusal, a retry or a fallback `warn`. `THERMITE_LOG_LEVEL` sets the lowest level a service writes (`info` unless set; a bad value stops it at start), and `SIGUSR2` switches a running service to `debug` and back; a rig's broker passes it on to the harness and the supervisor (goal 125).
- A rig's name follows one rule everywhere: 2 to 40 characters of a-z, 0-9 and -, starting and ending with a letter or digit. Add a rig on a machine took up to 63 characters before, which a cluster's namespace can't hold (goal 125).
- The merged by model and the review panel have one name everywhere, `merged_by` and `review_panel`: in the advisors file, `set_rig_model` (REST, MCP), the owner's messages (`message_agent`'s `to`), model usage records, advisor answers and field notes (`review_panel:<name>`), and between control, the supervisor and the harness. v0.1.0's names `combiner` and `panel` are refused: an advisors file that still has them stops the supervisor at start, naming the field, so rename them before the update. Control, the supervisor and the harness must be updated together. A rig's messages to the review panel that wait are kept (ledger schema 22), control's usage records take the new names (store schema 4, copied first), and records written before keep their words and show under the new names (goal 125).
- Every event names the run it is about, or none for a rig's own (a command, a check, the rig's settings): the harness's ledger works it out when it records the event (ledger schema 23, which also gives the events it already holds their run), the reports carry it, and control keeps it (store schema 5) and gives it as `run` in a rig's events over REST and MCP; events received before have none. A run's export takes the events whose run it is (goal 170).
- The harness's API answers a refusal with 409, input it can't use with 400 and a run it doesn't have with 404, as control's does, where some answered 500: the agents' model route on a harness that runs no agents, and a research tool given a report section's name it can't take. A command the harness refuses is applied and not accepted, with the reason, as before; control shows it `failed` (goal 125).
- A campaign's and a run's name take no dot: up to 64 lowercase letters, digits, dashes and underscores, starting with a letter or a digit. A campaign with a dot in its name is copied under a new name to go on; repositories, kits and cases keep their dots (goal 170).
- Rigs' reports can travel on a message bus: a NATS server with JetStream, the compose file's `nats` service with the `bus` profile. With `THERMITE_NATS_URL` set, the supervisor publishes each signed page of events to the rig's subject in the `REPORTS` stream and moves on once the bus has it; control reads the stream in order and takes each page with the ingest route's checks, which now live in one function for both. Without the setting, nothing changes. Commands and the other channels stay on HTTP (goal 168, step 0).
- Commands can travel on the message bus too. With `THERMITE_NATS_URL` set, control publishes each command it issues to the rig's subject in the `COMMANDS` stream, a work queue, as well as keeping it as before; the rig's supervisor takes it at once, delivers it to its harness as one it fetched, and acks it only once control has the outcome. A command reaches the harness within a fraction of a second, where it waited for the 5-second poll; the poll stays, every 3 minutes, for a command that never reached the bus. A command the owner cancels is taken off the bus. The largest signed command, 3.5 MiB, is one named constant. On the bus, a report page control refuses (a key that waits for the owner, a clock ahead) no longer leaves every later page refused as a gap: control's answer to the supervisor's figures names where control is in the rig's events, and when control is still behind what the supervisor sent a round before, the supervisor sends again from there, one page a round until control takes it (goal 168, step 1).
- Each rig signs in to the message bus with a key of its own. The supervisor makes a NATS user key (an nkey) the first time it starts with `THERMITE_NATS_URL`, keeps its seed in `bus-key.seed` in its state folder (0600; a full reset keeps it), and sends only the key's public part to control, as `bus_key` on its regular call to `POST /v1/rigs/<rig>/supervisor`, once before its first report. Control records it (store schema 7), keeps a new key for a rig as `rig_bus_key_changed` in its audit log and a step in the rig's history, refuses a value that is not a user key with 400, and writes every user to the NATS server's users file (`THERMITE_NATS_USERS_FILE`, required with the bus; `/nats-users/users.conf` on the compose file's new `nats-users` volume), which the server includes and reloads on control's request, through its system account, without a restart. Control's user may do everything; a rig's may publish only its own reports, take and ack only its own commands from its own consumer, and receive replies only under its own inbox; control's system user may only ask for the reload. Control's two keys are sealed in its store. The `nats` service waits for the users file before it starts, and its streams are in the `THERMITE` account now, so the ones an earlier bus kept are not read. A connection the client gave up on, as when the server dropped its user, is made again at the next call (goal 168, step 1).
- Live lines can travel on the message bus too. With `THERMITE_NATS_URL` set, the supervisor publishes them to the new `LIVE` stream instead of posting them to control: the harness hands over the lines of each source of each run (the planner's, the judge's, one trial's) as a message of their own, each signed as a batch over HTTP is, and each goes to its run's subject, `thermite.run.<run>.live.<source>`, or, for a line that names no run, the rig's, `thermite.rig.<rig>.live.<source>`; the supervisor's own lines go the same way, unsigned. The stream is a view: it keeps a message an hour at most, 1,000 messages of each subject and 256 MiB in all, the oldest going first, and a message holds at most 1 MiB. Control folds it with its consumer `control-live` into the same live view, with the same checks, and checks too that its run registry gives the run to the rig; a message it refuses is counted and logged as `live lines from the bus refused`. A rig's user may publish only its own live subjects and its runs', the newest 1,000 the run registry gives it; control looks at the users every 5 seconds now, where it looked every 60, and a run the bus doesn't open to the rig yet has its lines sent on the rig's own subject. The supervisor's figures count the lines it published and dropped there (`live`), by subject (goal 168, step 2).
- Live's pages get their new lines pushed: control sends each new line to a run's Live and a rig's whole Live as a server-sent event (`<page>/live/stream`), as soon as it has the line, from the bus or over HTTP alike, and the browser connects again on its own from the last line it has. The pages' `live.json` and their poll every 2 seconds are gone; REST's `GET /v1/rigs/<rig>/live` stays. A page that falls behind, with more than 500 lines waiting, keeps what it shows, gets the newest 500, and says how many it did not get.
- The message bus's state: `GET /v1/bus` and the MCP tool `bus_state`, for the owner's and the reader's tokens, give its server, the streams control makes with each consumer's backlog, and the live stream's figures from control and each rig's supervisor; `/metrics` adds `thermite_bus_*` and `thermite_live_*` series.
- A rig's configuration can travel on the message bus too. With `THERMITE_NATS_URL` set, control writes each rig's model route, advisors' routes and MCP servers with their sign-ins to the new `CONFIG` stream, a key-value bucket with one key for each (`thermite.rig.<rig>.config.model-route`, `.advisor-routes`, `.mcp-servers`) that keeps the latest of each, and only when a value changes: it looks every 5 seconds, and control started again reads the values' revisions back and writes nothing that did not change. Each value is sealed whole to the rig's own seal key, an X25519 key the supervisor makes beside its key on the bus (`bus-seal.pem`, 0600; a full reset keeps it) and registers on the same call (`bus_seal_key`; control's store schema version 9, a change of key in the audit log and the rig's history). The supervisor watches its rig's keys with its own consumer, `rig-<rig>-config`, applies each change at once (the route and the MCP servers to its harness, the advisors' routes from their next round), keeps what it knows while the bus is away or a message can't be taken, and no longer asks control for them every `THERMITE_MODEL_ROUTE_POLL_SECONDS`: on that beat it only hands its harness again what it lost. A rig may read only its own rig's keys, and only control writes them. Its figures count the updates it took and refused; `GET /v1/bus`, `bus_state` and `/metrics` show the bucket and these counts (goal 168).
- The message bus runs everywhere control does, and is on by default: the compose file's `nats` service needs no profile, and control and both supervisors use it unless `THERMITE_NATS_URL` is set to nothing in `.env`, which turns it off and sends everything over HTTP as before. Every connection is over TLS: control makes its own certificate authority at its first start with the bus (`bus-ca.pem` and `bus-ca.key`, beside its signing key, valid for 10 years), signs the server's certificate with it for the names the server is reached by (397 days, made again 30 days before its end, or when the names change, and taken by the server without a restart), and writes it with its key beside the server's users. `THERMITE_NATS_USERS_FILE` is now `THERMITE_NATS_CONFIG_DIR`, a folder (`/nats-config` in compose, the `nats-config` volume, where `nats-users` was), and the server runs as root with control's group to read its key. The bus's port, NATS's own 4222, is published on `127.0.0.1` by default, and on other addresses with `THERMITE_NATS_PUBLISH` (such as `0.0.0.0:4222`) for rigs on other machines and clusters. Rigs control sets up on a machine, on a cluster or with a join command get the bus's address (`THERMITE_NATS_PUBLIC_URL`, by default the host of `THERMITE_CONTROL_PUBLIC_URL` on port 4222) and the authority's certificate: on a machine as `bus/bus-ca.pem` beside the rig's other files (`THERMITE_NATS_CA_FILE`), on a cluster in the supervisor's environment (`THERMITE_NATS_CA`), and again at each update of the rig's images; the compose stack's supervisors read it from control's volume (`THERMITE_NATS_CA_EXPORT`); `thermite rig add` writes `keys/bus-ca.pem` and `THERMITE_NATS_URL` in `rig.env`, from `POST /v1/rigs`'s new `bus`. **Add a rig** shows the bus's address the rig will reach, as **Message bus**. A rig set up before keeps HTTP until its next update. A rig on RunPod keeps pull mode. Control's health answers with the bus too, `{"ok":true,"bus":"connected"}` (or `away`, or `off`), and stays 200 whatever the bus does. The compose smoke runs with the bus unless `THERMITE_NATS_URL=` is given; the rig deploy and cluster acceptance check that their rigs register on the bus; the release bundle runs the bus. A page tells how to check the bus, open its port and turn it off: [Run the message bus](docs/_site/src/content/docs/how-to/operate/message-bus.md) (goal 168).
- The message bus has a memory limit, 256 MiB, and its server's Go runtime is told 78% of it (`GOMEMLIMIT`), so that it frees the blocks a read loaded in time: without it, a read of a large stream got the server stopped at its limit. `THERMITE_NATS_MEMORY` in `.env` changes the limit, and `THERMITE_NATS_STORE` sets the most the bus keeps on its volume, by default 75% of the free space when it starts ([Run the message bus](docs/_site/src/content/docs/how-to/operate/message-bus.md#give-it-more-memory-or-disk); goal 168).
- The acceptance scripts run the container engine's own commands (build, run, exec, image prune) with Podman under `podman-compose`, however it is started, and with Docker under Docker's compose. They took the compose command's first word, so `COMPOSE="uvx podman-compose"` ran `uvx image prune`, and the campaign, cluster and rig deploy checks failed or refused under `podman-compose`.
- Control's own user on the message bus may not delete or purge the `EVENTS` stream, which is kept for good (goal 168).
- Control opens its port as soon as it starts, and until it has built its views from the message bus's events it answers every route 503, `control is starting: it builds its views from the events stream first`, and `/v1/health` 503 with `"starting":true` and the bus's state, so that a check waits and an operator sees why (goal 168).
- Two checks join `npm run check`: the size check (`npm run check:sizes`: no file over 800 lines grows) and the import-rule check (`npm run check:imports`: the parts of `src/` never import each other, and code outside a folder that is a module imports it through its `index.ts`), from the rules of shape added to CONVENTIONS.md (goal 125).
- Each API between the parts has one contract in `src/core/api/`: the harness's (for its supervisor, its advisors and the command line) and control's (for a rig's supervisor and for the owner's command line), each route with its path, its body's schema, the answer its caller reads and its limits, and both sides use it. The supervisor and the command line call them through one client each (`src/common/api/`), with typed errors. Every call of theirs to control or to the harness now ends after 5 minutes with no answer (30 minutes for a champion's patch or a kit's bundle), as a call that failed, made again at the next round; before, a call had no time limit. Where the two sides of a route held different limits, they are one now: the harness takes a command of at most 3.5 MiB, the largest that control signs (it took 4 MiB); the supervisor's figures carry an export's last error of up to 1,000 characters, as control takes (it cut them at 900); and the supervisor cuts a daily report longer than the 200,000 characters control keeps, and says so at its end, where control refused the report and the supervisor sent it again every round. Control's 404 for past research of a run it did not assign names its code, `not_assigned`, and the supervisor acts on the code, no longer on the words. The command line's calls to control carry its build in headers, as the supervisor's do. A body past its route's limit is answered 413 by control and by the harness, where both answered 500 with no words, so the supervisor's halving of a report page too large never started; the supervisor now also sends live lines too large for one call fewer at a time, where they stopped the rig's live view (goal 125, T2).
- Control keeps each rig's view and folds only the events that came since the last read, where it folded every event of the rig for each page, each `/metrics` scrape and each MCP call: at 200,000 events a read with nothing new takes about 1 ms and one after 100 new events about 9 ms, where each took about a second. A control that starts folds each rig's events once, at the first read (goals 125 and 168).
- Control's store keeps an index of each rig's events by ledger and order (store schema version 8; the store is copied before it migrates), so a view's pages of events start where the last ended: the first read of a rig's view after control starts takes about 0.4 s at 200,000 events, where it took about 1 s, and grows with the events, no longer faster.
- A run, and what it owns, is addressed through its campaign and its name, never through its rig, since a run's name is used once on control (goal 170). The old addresses are gone, with no redirect: a bookmark or a script that uses one needs the new one.
  - Dashboard: a run's page is `/ui/campaigns/<campaign>/runs/<run>` and each tab adds its name (`/attempts`, `/history`, `/planner`…), where it was `/ui/campaigns/<campaign>?run=<rig>/<run>&view=<tab>`; an attempt's page is `…/runs/<run>/attempts/<attempt>`, where it was `/ui/rigs/<rig>/attempts/<attempt>`; a run's Live is `…/runs/<run>/live`, where it was `/ui/live?run=<rig>/<run>`; its paper and champion patches are `…/runs/<run>/paper.md` and `…/runs/<run>/champions/<seq>.patch`, where they hung from `/ui/rigs/<rig>/runs/<run>`. The breadcrumbs read Campaigns › campaign › run › attempt. **Start a run** and New campaign open the new run's page, which says `Starting <run> on <rig>.` until the rig reports the run. A rig's page and its whole Live keep the rig's address.
  - REST: `GET /v1/runs/<run>`, `/v1/runs/<run>/untried`, `/v1/runs/<run>/directions` and `/v1/runs/<run>/champions/<seq>/patch`, where they were under `/v1/rigs/<rig>/runs/<run>` and `/v1/rigs/<rig>/champions/<run>/<seq>/patch` (the rig's own upload of a patch stays under the rig). `POST /v1/propagate` takes `{run, to_run}`, where it took `{from_rig, run, to_rig, to_run}`; `GET /v1/usage` takes a run without `rig`, and its run scope is `{kind: "run", run}`; `POST /v1/campaigns/<campaign>/runs` takes `queue_from` as the run's name, where it took `{rig, run}`.
  - MCP: `get_run`, `run_queue`, `trial_session` and `model_usage` take a run without a rig (`trial_session`'s `run` is now required, and its answers name the rig as a fact); `propagate_champion` takes `{run, to_run}`; `start_run`'s `queue_from` is the run's name.
  - Commands: a kind about one run (its payload's `run`, such as `pause_run` or `message_agent`) goes to the rig the run is on, so `POST /v1/commands`, MCP's `issue_command` and `thermite command` may leave the rig out; a rig given that is not the run's is refused in words.
  - The command line: `--queue-from RUN`, where it took `RUN` on `--rig` or `RIG/RUN`; `thermite command --rig` may be left out for a kind about one run.
- One attempt of a run can be read by itself: `GET /v1/runs/<run>/attempts/<attempt>` and MCP's new `get_attempt {run, attempt}` give the attempt as `get_run` has it, the rig it ran on, whether the run is an earlier one, and the champion it became (goal 170).
- A run's history stays on control when its rig is retired or fully reset (goal 170). Control reads each run from its record of the runs and from the events it keeps of the run's own ledger, so such a run stays on its campaign's page, under **Earlier runs**, marked `on <rig>, retired` or `before <rig>'s full reset`, and opens like any run: its tabs, its attempts, its champions' patches and its Live, and over REST and MCP. It runs no more: a command to it is refused in words (`Run <run> is an earlier run: …`). **Start a run** can copy its untried experiments. Control keeps the views of the 16 earlier ledgers read last (goal 168's kept views). A name used by two runs before v0.1.1, on two rigs or again after a full reset, stands for the newest of them.
- The synthesizer and the final writer, a research run's writers of its answer cards and of its paper, have model slots of their own: lines **Synthesizer** and **Final writer** under **The advisors** on **Edit rig**, each with its model, effort, **Runs in** and context, and `agent` `synthesizer` or `final_writer` in `set_rig_model` (REST and MCP) and `rig_models`. With none, each uses the first teacher's model, as before; with one, it runs with the teachers switched off too. The advisors' routes carry them as `synthesizer` and `final_writer`, over HTTP and on the message bus, and their calls are recorded under their own names. Control's store moves to schema version 10 (copied before it migrates) for the two slots (goal 166).
- You can add your own words to an agent role for one campaign, with no change to Thermite's code: the contract's new `role_additions`, one text for each role by its id (`worker`, `planner`, `teacher`, `merged-by`, `auditor`, `reviewer`, or a research campaign's `research-worker`, `research-planner`, `research-teacher`, `research-merged-by`, `research-reviewer`, `synthesizer` and `final-writer`), at most 20,000 characters each. Every prompt of the role carries its addition as a section of its own after the role's text, labelled as the owner's with the contract's version, and its record shows the source `owner's addition`; it adds to the role's text and never replaces it. A role the campaign's mode never runs is refused. Set them on **New campaign**, on the campaign's page (**Your additions to the agents' roles**), with `POST /v1/campaigns/<campaign>/additions`, the MCP tool `set_campaign_additions` or `thermite campaign additions`; each saves a new version of the contract, signed into every assignment. A rig whose harness is older refuses a contract with them (goal 166).
- Every prompt Thermite sends an agent comes from its role's definition in `src/agents/roles/`: one function for each role puts its prompt together for a run (the worker's, the planner's, each advisor's, the model check's and compaction's), and a test fails when a prompt is built anywhere else. The prompts sent are the same, word for word (goal 166).
- Every prompt a run's agents are sent is kept whole, compressed, in the rig's ledger and in the run's export (`prompts.jsonl.gz`), never in the run's research folder. Control gets an `agent_prompt` event for each, with its sections and where each comes from. A run's new **Prompts** tab, the **Agents** page and each role's page show them, and so do `GET /v1/agents`, `GET /v1/agents/<role>`, `GET /v1/runs/<run>/prompts` and `GET /v1/runs/<run>/prompts/<id>`, the MCP tools `agent_roles` and `agent_prompts` (owner and operator), and `thermite agents list` and `thermite agents show`. The rig's own API previews a worker's or the planner's next prompt with no side effect (goal 166).
- A worker's or a planner's first message is cut to fit its model's window, by the advisors' rule (the compaction point less 30%): the owner's messages and the role's own text stay whole, and the message says what was cut and where the rest is. Before, a message larger than the window failed every call of the trial or round (goal 166).
- Claude Code, Codex and OpenCode no longer read the project's `CLAUDE.md` or `AGENTS.md`: an agent's prompt is only what its role's definition rendered. OpenCode starts with `OPENCODE_DISABLE_PROJECT_CONFIG=1`, a worker's and an advisor's, so it reads no configuration of the project's either; its read tool still adds an `AGENTS.md` it finds in a folder below the workspace's top when the agent reads a file there, which no OpenCode setting turns off (goal 166).
- What an agent is told after its first message, inside the same call, comes from its role's definition too, word for word as before: the nudge to a worker that stopped without submitting, the warning that a trial's turns or time are nearly spent, the lines after a cut-off reply, a full context or a failed model call, the owner's message put to a running trial, and the message an agent in Pi goes on from after a compaction. Each is kept as the first message is, in the ledger (migration 25), the run's export and its `agent_prompt` event, with `turn`, its place in the call (0 for the first message); the harness's `GET /v1/runs/<run>/prompts` lists it, and a test fails when one is sent from anywhere else (goal 166).
- The final writer's model calls are recorded under its own name, `final_writer`, on **Model use**, `GET /v1/usage` and `model_usage`, not as the teachers' (goal 166).

### Campaigns

- The owner can withdraw bad evidence (goal 174): an attempt, for good, with every attempt built on it, or the measurements of one of the judge's jobs, whose attempts are measured again. The signed command `invalidate_evidence` is the owner's alone (an operator's, an agent's and an advisor's are refused), and goes in two steps: a preview, in which the harness says what it would reach (the attempts, the verdicts it supersedes, the judge's jobs it cancels or queues, the champions it reopens and where the run's champion moves) and changes nothing, then the withdrawal, which names the preview's sha and does exactly that or is refused. Nothing is deleted: each attempt reached gets an `invalidated` verdict over the one before, champions that rested on it are reopened, the run's champion moves back with a `champion_moved_back` event and its git ref follows, a change a trial still builds on a withdrawn attempt is withdrawn as it arrives, and a published champion's patch stays in the results repository. On the dashboard, **Withdraw its evidence…** on an attempt's page shows what it decides before **Withdraw the evidence**, and the page then says what it reached, when, by whom and why, with the chip **Withdrawn**; `thermite invalidate`, REST and MCP's `issue_command` give the preview first too. Every step is an event, so control's views, the run's History, the exports and the knowledge base show it. [Withdraw bad evidence](docs/_site/src/content/docs/how-to/campaigns/withdraw-bad-evidence.md) shows how.
- A Pi worker is reminded once 85% of its trial's time is used (when the trial has a time limit): submit its best working change now, and, in a trial that measures rather than changes the code, record what it measured as notes, with the numbers, before it starts another measurement.
- A teacher's opportunity is no longer left out for a part longer than its limit, such as a `gain_bound` over 300 characters: the part is cut to its limit.
- A reviewer's answer of the review panel is no longer thrown away for a reason longer than 8,000 characters (it is cut) or for a field of its own (it is dropped). A research task's yield no longer has `no_question`.
- A research run's reviewers, teachers and workers are told that the run measures nothing: its evidence is what archived sources say. A question is answered when its claims give the best answer sources allow; what only a measurement on the target could settle is named as a next experiment, for a goal or hill-climb run, and is not a gap. Before, reviewers could fail a research run for a test on its hardware that no research trial can run, so it never ended.
- A hill climb's baseline that failed in the rig itself, not for its starting point, is tried again at once, as a candidate's `crash_infra` is; only after a second such failure does each next try wait 10 minutes. Before, the first such failure held the run for 10 minutes.
- A research review's package is no longer cut at 200,000 characters without a word. Before, a run with many hypotheses lost its newest ones, and its criteria, from the end of the reviewers' prompt, and its review could not pass.

A verdict's word counts in any case, and a field over its limit is cut instead of the whole item being dropped. Before, one missing verdict among a run's hypotheses failed the whole review.
- A review whose reviewers keep failing is posted as not passed at its fifth try, or any later one, with each reviewer that gave no answer failing it and why. Before, it waited after the fifth try with no one to post it, and a research run that waited on it could not end.
- An advisor in Pi whose answer is refused for the same problems three times running ends its call with those problems as its error, in place of being asked again without end; the call then fails as any advisor's call with no answer does.

- The progress rule (goal 117): at each digest after the minimum, `research_progress` says whether every open question is saturated (its last 4 tasks added no verified claim from a new site, and its card's certainty did not rise: a card rewritten in other words at the same certainty, as the synthesizer does each round, is no progress) and how long the run has gone without an improved decision or a more certain card. When both hold for a quarter of the running time (and of the minimum), no review waits and some item is open, the run ends with its open items stated (`research_stopped`): the final writer writes its paper, whose package says which questions stayed open (`end`, `stayed_open`), and the run closes with `research stopped adding: its open questions are saturated`. No time cap is added: the rule holds only once research stopped adding. The paper's verdicts are the review panel's decisions, and a question with no verified claim needs no citation in its results.

### Operate

- A subscription's usage on **Providers** (goal 151): a Claude or ChatGPT subscription's row shows its windows on its closed line (`5-hour 42%`, `Weekly 81%`, marked from 80%), and in full when open, with when each resets. A ChatGPT subscription's come from ChatGPT's usage endpoint, which control asks with the sign-in at most every 5 minutes; a refusal is said in words, with a link to ChatGPT's **Settings › Usage**. The harness reads both forms of Claude Code's rate-limit event (all windows in `unifiedWindows`, or the one window the Claude Agent SDK's type names) and keeps each window until a later event changes it, across trials too. OpenAI refuses its usage endpoint for a sign-in for open-source apps (HTTP 401), so a ChatGPT subscription's row shows the refusal and the link. The MCP tool `providers` gives each subscription's `usage`.
- A run's trial length can change while it runs: a `trial_minutes` rule (`redirect` over the command line, REST or MCP, `value` in minutes from 1 to 1440) comes before the contract's `lanes.limits.trial_minutes` and the rig's setting, from the next trial on. The **Planner** tab shows it as `Trials last <n> minutes`. Before, a campaign's trial length was fixed for its runs.
- A run's lanes can keep working while the judge works: with the contract's `lanes.keep_working`, or a run's `keep_working` rule (`on` or `off`, `redirect` over the command line, REST or MCP), a lane's next trial starts as soon as its last one ends and a round ends when its trials end, while the judge works through their changes, at most `budget.max_open_attempts` of them. Off by default: lanes wait for the judge's verdicts, as before.
- A round no longer holds a lane behind another lane's trial (goal 136). It ends once every free lane has run its trials, and a lane still on a long trial joins the next round when its trial ends. A change waiting for the judge still holds the round, unless the run keeps working. In a research run, a task the round holds for a lane still on an earlier round's trial does not count as its question's task in the round, so a free lane can take that question too. Before, one long trial left every other lane idle until it ended.
- A research worker's fetch refused for a reason that lasts (too large, outside the campaign's sites, `robots.txt`, a private address) is answered at once when the run asks for the same URL again, with no new download: the answer says it was refused before, how many times it was asked for, and to look for the same text elsewhere (goal 136). Before, a worker could fetch the same large PDF every few minutes for hours. A page that crossed `fetch_policy.max_bytes` in its last part is refused, not returned cut short.
- A research run's clock stops while its rig drains before an image update, as it does while the agents are stopped: its durations and its progress rule leave the drain out (goal 136). As it starts again, the harness records the drain's end (`rig_drain`, `drain: false`, `the harness started again`).
- A draining rig's page says what the drain waits for (goal 136). A card at the top says since when it drains, who asked and why, and what it waits for, with **End the drain**. Under **At work**, each trial it waits for has a row under its lane: how long it has run, what it last did, a page it keeps asking for that the run refused (`repeats a refused request`), its work so far, and **Stop this trial…**. The new signed command `stop_trial`, the owner's and an operator's, ends one trial as interrupted and puts its experiment back at the top of the queue. While a rig drains, its report lists each open trial (`work.open`), and `work.draining` says who asked (`by`). Before, the page said only how many trials ran, and only on a rig control set up on a cluster.
- A change written on an older champion is carried to the new one: when it becomes champion, the champion it replaced is ported onto it; when it loses to the current champion, the judge measures it against the champion it was written on (`parent_screen`, event `parent_screened`), and if it helped there, ports it onto the current one. A port is an experiment at the top of the queue, `Port <attempt> onto champion #<n>`, with the original diff, which a worker implements and the judge judges as any change (`port_queued`). Before, such a change was judged only against a champion it was not written on, and its effect was lost.
- The judge builds in parallel: on a rig with several judge GPUs, each card builds as a builder user of its own (`builder`, `builder-1` … `builder-7`), so two changes build at once; a change two cards need is built once, and the second waits for it. The isolation selftest probes each card's builder, and a new probe, `build-work`, checks that no other role can reach a build under way. Before, every build on the rig waited for the one before it. A build's key is now the image's installed packages and compilers, with `THERMITE_TOOLCHAIN_ID` for a tool installed another way, not the image's name: an update to new images with the same packages keeps the run's builds.
- A judge job no longer loses its lease to a long build. The judge renews the lease every few minutes while it builds, and while it waits for another executor's build; before, a project whose build took longer than the 15-minute lease, with the wait, was built again and again until its job was blocked, and its attempt was never judged. A blocked job's attempt now ends as `errored` ("failed in the judge"), so its lane's round ends and the next starts; before, the attempt stayed `building` and the run's lanes waited for it. When the harness starts, each blocked job is queued once more (`job_unblocked`), its attempt with it, and one more lost lease blocks it again.
- Take a rig's results off it from the dashboard. **Export**, in the header of a rig's page and of a run's page, asks which export: **What changed** since the last one, or **Full export**, which also holds a snapshot of the ledger, every run's research folder, finished or not, and the pages each run fetched. The line at the top of the page says the export was asked for and that it shows on the **Exports** page when all its files reach control. A full export now holds the research folder of every research run, and of every hill-climb or goal run that recorded research, even one still running or paused, at `research/<run>/folder-<export>/`, so a broken run's record leaves the rig whole; normal exports are as before. The new **Exports** page, in the sidebar and linked from each rig's page, lists every export control keeps, for every rig, newest first: its kind, when it was made and completed, its events, files and size. **Download** gives a complete one as one `<rig>-<export>.tar.gz` with its manifest; over REST, `GET /v1/rigs/<rig>/exports/<name>/archive` with the owner's token, and the MCP tool `exports` lists them for the owner and an operator.
- The dashboard says how a run ended. A closed goal run that met its goals reads **Completed**; any other closed run reads **Finished**. With no run at work, a campaign shows its newest run's state, so a campaign whose newest run completed reads **Completed** even with an older run paused. The Campaigns list counts such a campaign as finished, which the default filter hides, and counts its runs as "N completed" apart from "N finished". `get_run` and a rig's view give `goals_complete`.
- A judge-only run, started with its agents off, says so: `judge only` after its mode under its name, a box on its page (`Judge only: No workers run. …`), the mark **judge only** on its cards and under **Earlier runs**, and, while experiments wait in its queue, a line on its **Experiments** tab: no worker takes them, and its **Start a run** link opens the campaign's Start a run panel with that run chosen under **Copy the untried experiments of**.
- A run's goals show their whole text: a long goal, or the judge's long reason, shows its start and **more** opens the rest.
- A decision you make leaves **Needs you** at once, with its count; the change's own page still says what you chose and what the rig did. It comes back only if the rig refuses it or the item needs you again.
- A dashboard button that sends something to a rig says at once that the click took, then follows it to its outcome, with no refresh. The button turns into **Sending…**, a line says `Sent to rig-1 at 03:41 UTC. Waiting for the rig to take it.`, then that the rig took it, then `Done.`, and the parts of the page that it changes are drawn again. A refusal or an expired command says why, and the button comes back. A rig check's row goes from **sent** to **running** with the time so far, such as `running · 1 m 12 s`, and what the check pauses, to its result in place. This covers every command's button (**Run it**, **Check**, **Pause**, **Resume**, **Restart the lanes**, **Export**, the decisions, the experiment queue and the rules), a message to the agents, **Use** on Providers, **Update to** a version, **Update to these images** and the other buttons of a rig that control set up, **Save changes** on **Edit rig**, and **Start a run**, whose page opens the run's own page once the rig reports it. Without the page's script, each form posts as before, and the page it lands on says `Sent`.
- Model usage. Code records each model call of the workers, the planner and the advisors, never an agent, as a `model_call` event of its run: its tokens in (cached and not cached), its tokens out with the reasoning, and its times, as far as Pi, OpenCode v2, Codex and Claude Code report them. A figure a program does not report is null, never 0. Control sums the records for a run, a campaign (all its runs on every rig) or the whole system, today, over 7 days or for all time, with output tokens a second (median, 10th and 90th percentile) and the cost: each call's tokens at its model's price (the provider's list's, as OpenRouter and Nous Portal give one, else one the owner sets with `POST /v1/model-prices` or the MCP tool `set_model_price`), "on a plan" for a subscription's calls, "no price" where none is known, and a RunPod rig's pod spend for the run it ran: `GET /v1/usage` and the MCP tool `model_usage`.
- Model use on the screens: a run's page shows one line (trials, rounds, its time, its time in calls) and two cards (cost; tokens in, out and tok/s) above its tabs, and its new Stats tab shows its calls in each round and the table by agent and model; a campaign's page shows its model use in its sidebar, with each run; the new Metrics page shows the whole system's, by model and by campaign, for today (in the viewer's time zone), 7 days or all; Settings › Providers has one Model prices table under the providers, which takes your price for each model (In, Cached in, Out, in $ for a million tokens) and shows the provider's own. `GET /v1/usage` and `model_usage` take `tz`.
- Control's log pages through every entry, in the dashboard, over REST and in the `control_log` MCP tool.
- A worker trial's session is read over MCP with `trial_session` (goal 139): with a rig alone, each trial whose lines control still has, newest first, with what it was asked, its newest tool call and how it ended; with a trial, its lines (thinking, text, tool calls, results), oldest first, a page at a time with `after` and `next_after`. Its answer keeps to 40,000 characters, as `get_run`'s does. The owner, operators and readers get it; a campaign's agents don't.
- A model's long tool call no longer stalls the process that streams it (goal 140). Pi's model client parsed a tool call's whole arguments again on each piece that streamed in, so the work grew with the square of their length: a call of about a megabyte held a rig's supervisor for over an hour, with no report, command or live line. Past 16 KiB, the arguments are now parsed only when the call ends, as every provider already did. Thermite applies this to pi-ai 1.3.0 at install (`scripts/patch-pi-ai.mjs`), and the install stops on any other version until its parser is checked.
- A hill climb's champion is at the top of its run's page (goal 142): a card left of **Cost** with the champion's value of the main metric, such as `14.6 tok/s`, and its gain over the starting point, with the starting point's value. The judge now records the values a gain comes from: since goal 133 it read its measurement blocks with metric and case swapped, so each verdict had no values, and the gain chart gave the starting point's value beside the champion's gain. A champion judged before the fix shows an estimate from the starting point's value and its gain, marked `≈`; the leaderboard's `values` says so with `estimated`.
- An optional limit on a worker's field notes in one reply (goal 147): the contract's `lanes.limits.notes_per_turn`. A Pi worker's note past it is refused in words and its trial goes on. There is no limit unless the contract sets one.
- A trial's clock (goal 144). A worker's brief gives the time its trial ends, in UTC. From 75% of a trial's length, each of a Pi worker's tool results ends with the time left. A Pi worker's command (`run`, `dev_run`) stops 3 minutes before the trial's end, so that the worker can still submit. At the end, a tool that still runs answers at once: the trial ends as `wall` with its notes, not as `worker process gave no result` two minutes later with none. A lane's ccache now hits across its trials: `CCACHE_BASEDIR` is the lane's folder and `CCACHE_NOHASHDIR` is on, where each trial's new checkout folder made it miss nearly every compile.
- A stuck trial asks you (goal 143). A trial that makes the same tool call with the same answer 10 times in a row, that asks 10 times for a page the run refused before, or that sends no line for longer than **Ask me after a quiet spell of (minutes)** on **Edit rig** (none by default; `quiet_minutes` over REST and MCP), is a card under **Needs you**: **Repeats** or **Stuck?**, with how long it has run, what it last did, a Pi worker's open model call (since when, and how much the model sent so far) and the calls it repeats behind the card, and **Stop this trial…** (the stop records why) or **Leave it running**. Its lane's row gets a chip. Nothing ends a trial for being quiet or repeating.
- A Pi worker's repeated tool call gets a short answer (goal 143): a call with the same tool, arguments and answer as one already in the conversation is answered `Same call and same answer as at <time> UTC (call <n>). …`, so a model in a loop no longer fills its context window. The call still runs; a changed answer, or one after a compaction, is given in full. Every harness's repeats show as a `trial_repeating` event and a line in **Live**.
- What each lane's trial is doing is in the rig's report, in `get_run`'s and `run_queue`'s `at_work` (`last_line_at`, `reply`, `repeating`) and in the teachers' brief (goal 143). Control keeps each open trial's newest 400 live lines past the rig's window of 20,000, so one trial's flood can't push out another's lines.
- A request the harness refuses says which field and why (goal 143), such as `invalid request: quotes[0].quote has 9 characters; it needs at least 20`, for every endpoint a worker calls, through Pi's tools and `thermite-trial` alike. `add_claim`'s text and `thermite-trial research help` give a claim's limits.

- The judge's smoke check passes on a machine with noisy timing when the only wrong result is the no-op's `inconclusive` in place of `neutral`. It then says so in a note: the timing on this machine is noisy, and results there need more repeats. Any other wrong result still fails it.
- The CUDA smoke check works on newer GPUs. Its kit builds native code for every GPU generation its CUDA builds for (with CUDA 12, Pascal to Hopper, `sm_60` to `sm_90`; with CUDA 13, Turing to Blackwell, `sm_75` to `sm_120`), with PTX for newer ones, so no run compiles the kernel when it starts. Each case does five times the work, and its known win is register tiling, several times faster than the naive kernel. Before, on an Ampere card, starting the process took most of each run, and the known win of shared-memory tiling came out at 8%, under the contract's 10%.
- The documentation site has tutorials, how-to guides, reference and explanation. Agents read it through `llms.txt`. It includes the known limits and the security model.

- Faster checks. `npm test` runs the test files side by side, one for each CPU, then the judge's and the broker's one at a time, alone, because they time real processes (`--part parallel` or `--part alone` runs one of the two). CI runs the two parts in separate jobs at the same time, and no job waits for another. Tests that need judged attempts but do not test the judge get the real judge with a stand-in runner, which answers the test kit's runs and checks of its stock kernels in the test's own process; the judge's own tests keep real runs. The heavy CI jobs (the compose smoke test, the rig image, RunPod and the quick start) run on a push or a pull request only when the change touches what they test; every job runs on a version tag and when CI is run by hand.

A maintainer can also publish a build between releases by hand, tagged with its commit only and checked the same way, for a lab to pin by digest. A release's `compose.yaml` sets the RunPod test image to the release's rig image too.
- `get_run` stays a size an agent can read for a run of any length: each list that grows with the run (the journal, the timeline, the queue, the hypotheses and the others) gives its newest 10 entries by default, and the research report its first 4,000 characters, with `cut` saying what was left out. `limit`, `list` with `offset`, and `full_report` read the rest. A research run of a day and a half gave 3.2 million characters; it now gives about 85,000. The same is over REST, `GET /v1/rigs/<rig>/runs/<run>`, new.
- `get_run` and its REST route keep their default answer under 40,000 characters as MCP sends it, inside an agent's tool output: above it, the texts in the lists' entries are cut, shorter each step, and `cut` says so; `list` gives a list whole. `run_queue` keeps to the same budget, every entry kept. `rig_setup` gives a rig's newest 20 steps (`steps` asks for up to 500) with `steps_total`.

Before, **Export** on a run's page exported the whole rig, every run included.

### Removed

- The outside knowledge base: its copies of campaign folders, the advisors' search grant and `THERMITE_OUTSIDE_KB_SYNC_SECONDS`. At the update, each one becomes an MCP server with its token, and a kit names it.
- The old `QWEN_*` names of the model settings, the `thermite-qwen` provider ID and the `qwen-api-key` file migration. Use the `THERMITE_MODEL_*` settings.
